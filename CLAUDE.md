# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Nu — project intent

A continuation of the original Mu Editor for the Python programming language (reference: https://github.com/mu-editor/mu).

The original maintainers archived the upstream GitHub repo. This fork exists so the maintainer's child and the wider community can keep using it safely into the future, with modernization as needed.

**Goal: maintain and modernize.**

## What this is

This repo is **"nu"** (`github.com/kovirlabs/nu`), a fork of the **Mu editor** (`github.com/mu-editor/mu`, the `upstream` remote). Mu is a modal Python code editor for beginner programmers, built on Qt (PyQt5 upstream; PyQt6 here). Upstream was archived/marked unmaintained; this fork's stated goal is to keep it usable and modernize it as needed.

The actual editor lives in `mu/`. The distribution is published as `nu-editor` (the fork's own PyPI identity, renamed from the inherited `mu-editor`); the version is **2.0.0b3** — nu's own line, major-bumped from upstream Mu 1.2.2 to mark the breaking Qt6/Python-3.11+ modernization (a continuation, not a reset). The importable package stays `mu` and the version lives in `mu/__init__.py`. The user-facing display name is **"Nu"**: the in-app strings (window title, dialogs, tooltips, messages) were renamed from the inherited "Mu", and the installer ships under the Briefcase `formal_name` "Nu Editor" (see `pyproject.toml`). Deliberate **heritage/credit references to the original Mu are kept** — AUTHORS, the in-app "Mu was created by Nicholas H. Tollervey" note, upstream links, and internal logs/comments — so "Mu" still appears where it refers to the upstream project rather than this app's name.

`main.py` at the repo root is a stray PyCharm sample — not part of the project; ignore it.

Since **Phase 1d** (see `TODO.md`) `pyproject.toml` is the **single, canonical packaging definition**, built with the **hatchling** backend (`make dist` → `python -m build`); `setup.py` and `setup.cfg` were retired and their config (deps, pytest, coverage, lint) folded into `pyproject.toml`. `uv.lock` pins the resolved dev environment. The version is read from `mu/__init__.py` via `[tool.hatch.version]`; `[tool.briefcase] version` in `pyproject.toml` duplicates it as a literal, so bump both. Native **installers** are built with **Briefcase** (Phase 4; upstream's `pup` pipeline, `conf/` and `debian/` were retired in 4e): `.github/workflows/build.yml` builds the Windows `.msi`, macOS zipped `.app` and Linux `.AppImage` on a manual run or a `v*` tag, and a tag publishes a GitHub Release. Builds are unsigned for now. See `docs/packaging.md`. The Briefcase app id is **`org.kovir.mu`** (`bundle` + app key); `mu/app.py`'s `setDesktopFileName` must match it.

## Runtime constraints

As of **Phase 2** (see `TODO.md`) Mu runs on **PyQt6** and **Python 3.11+** (verified green through **3.14**). `pyproject.toml` declares `requires-python = ">=3.11"` and depends on `PyQt6>=6.6`, `PyQt6-QScintilla>=2.14`, `PyQt6-Charts>=6.6`, with a modern Jupyter stack (`qtconsole>=5.5`, `ipykernel>=6.29`, `jupyter-client>=8.0`). The old frozen Py3.5-era pins are gone. Since Phase 1c, **ruff** (not black) is the dev linter+formatter; `black` (`>=24`) is now *only* a runtime dependency powering the in-editor "Tidy" button (`mu/logic.py`), so don't drop it. The old `black<22.1.0` + `click<=8.0.4` pins were removed in Phase 1d — old black crashed on Python 3.12+ (`ast.Str` was removed), and click now comes in transitively via black.

`uv sync` auto-downloads a managed CPython into `.venv` and installs the project editable. The system `python3` here is 3.14; prefer working through the uv venv (or any 3.11+ virtualenv).

## Common commands

Dev setup with uv (preferred): `uv sync` installs the runtime dependencies into `.venv` using a managed CPython 3.11; add `--extra dev` (or `--all-extras`) for the tests/docs/packaging/i18n tooling. Run things with `uv run python run.py`, `uv run python -m mu`, or `uv run pytest`. The repo is a **uv workspace** (`plugins/*` are members): `uv sync` also installs the bundled plugins (today `nu-circuitpython` and `nu-pygamezero`) editable, because `nu-editor` depends on them via `[tool.uv.sources]`. Relock with the venv's uv (`.venv/bin/uv lock`, currently newer than `~/.local/bin/uv`) to keep the lockfile revision stable.

Dev setup without uv (inside any 3.11+ virtualenv): `pip install -e ./plugins/circuitpython -e ./plugins/pygamezero -e ".[dev]"` installs runtime + tests + docs + packaging + i18n extras (pip doesn't read `[tool.uv.sources]`, so bundled plugins need their paths given).

Most workflows go through the `Makefile` (which delegates to `make.py`):

- `make run` — run the local dev build (requires an active virtualenv; equivalent to `python run.py` or `python -m mu`).
- `make test` — full test suite (`pytest -v --random-order`). Sets `LANG=en_GB.utf8`; locale-sensitive tests need this.
- `make coverage` — tests with coverage report (`--cov=mu --cov=plugins`, over `tests/` and `plugins/`). Upstream maintained 100% coverage; `mu/plugin` is at 100%.
- `make lint` — lint with **ruff**.
- `make format` — check formatting; `make tidy` — reformat in place with ruff. Ruff wraps and lints at **88** columns (single `line-length` in `pyproject.toml` `[tool.ruff]`; the old black-79/flake8-88 split is gone).
- `make check` — runs `format` + `lint` + `coverage`; this is the pre-commit gate.
- `make dist` — build sdist/wheel. `make win64`/`macos`/`linux` build platform installers locally via Briefcase (CI's `build.yml` is the release path).

**Run a single test** (the Makefile has no target for this): `pytest tests/test_logic.py::test_name`. pytest collects `tests/` and `plugins/` (`testpaths`), with the bundled plugins' source folders on `pythonpath`. Note that `addopts = --random-order` is set in `pyproject.toml` (`[tool.pytest.ini_options]`), so test order is randomized by default (pytest-random-order) — add `--random-order-bucket=none` for file order or `--random-order-seed=...` to repeat a run. (`-p no:randomly` is a no-op here: it disables pytest-randomly, which Nu doesn't use.)

**Running tests headlessly** (no display, e.g. via uv): the Qt tests need a platform plugin, so set `QT_QPA_PLATFORM=offscreen`. Full incantation used during development:
```
QT_QPA_PLATFORM=offscreen LANG=en_GB.utf8 uv run --no-sync pytest -q --random-order-bucket=none
```
(On a box where `/tmp` is mounted noexec, add `--basetemp=$HOME/.cache/nu-pytest/bt`: one test builds and runs a real venv in its `tmp_path`.) Current green baseline (Python 3.11 + PyQt6, with `--all-extras` so the opt-in micro:bit plugin is installed): **1638 passed, 20 skipped** (counts can shift by one between Python versions). The test session is **isolated**: before anything imports `mu`, the root `conftest.py` sets `MU_DATA_DIR`, `MU_HOME_DIR` (both honoured by `mu/config.py`) and `IPYTHONDIR` to a throwaway folder and gives the single-instance lock its own name, so tests never touch the real `~/.local/share/mu`, `~/mu_code` or IPython profile, and they run fine while a real Nu is open (`tests/test_config.py` checks this). Every test file passes on its own and in `--random-order`; autouse fixtures fail a test that really quits the `QApplication` (patch `QCoreApplication.exit`) and restore `sys.excepthook`/`threading.excepthook`. On a headless box without Mesa, Qt6's `offscreen` plugin still needs `libEGL.so.1` — put it on `LD_LIBRARY_PATH` (e.g. `apt-get download libegl1 libglvnd0 && dpkg -x` into a local dir). Lint the project's way with `uv run --no-sync python -m ruff check` and reformat with `... ruff format` (config in `pyproject.toml` `[tool.ruff]`; the gettext `_` builtin is declared there as `builtins = ["_"]`, so no env var dance is needed).

Test layout mirrors the source tree: `tests/test_logic.py` tests `mu/logic.py`, `tests/modes/` tests `mu/modes/`, etc.; each bundled plugin's tests are in `plugins/<name>/tests/`. Shared autouse fixtures (QApplication, no autosave, temp drop-in plugins dir, plugin error handler and plugin image registry resets, the quit and exception-hook guards) and the session isolation are in the root `conftest.py`.

Every text file is LF (`.gitattributes`: `* text=auto eol=lf`, binaries marked); the few files once committed with CRLF were normalised, so no file needs special line-ending care.

## Architecture

Mu is a **modal editor**: a fixed core of always-available features, plus a set of *modes* that retarget the editor at different platforms. This fork has trimmed the upstream set to four, plus micro:bit back as an opt-in plugin (see `TODO.md` for the rationale): **python, debugger, circuitpython, pygamezero**, and **microbit** (opt-in). The **core** modes are just **python** and **debugger** (the locked core/plugin boundary); **circuitpython** and **pygamezero** are **bundled plugins** (`plugins/circuitpython` + `plugins/pygamezero`, packages `nu-circuitpython` + `nu-pygamezero`, loaded through their `mu.plugins` entry points, switched on by default, mode keys unchanged). The core must not name or import them. Upstream also shipped esp/pico/pyboard/lego/snek/web/microbit — removed. **microbit** is back (Phase 6) as an **opt-in** workspace plugin, `plugins/microbit` (`nu-microbit`, mode key `microbit`): installed only via the root `microbit` extra (`uv sync --all-extras`), NOT a `nu-editor` dependency, not in Briefcase `requires` or `loader.BUNDLED_DISTRIBUTIONS` (so it shows as an "Installed package") until the maintainer validates it on hardware (checklist in its README; promotion is 6c). It flashes with mpremote's in-process `SerialTransport` + DAPLink drive copy, firmware pinned by URL+sha256 and downloaded to `DATA_DIR/microbit/firmware/` (never vendored); its GUI-free `flash.FlashJob` state machine runs on a `QThread` (`worker.py`) — never drop a running `QThread`'s last reference, nor leave one running for Qt to destroy with its parent at exit (Qt aborts; the debugger client's listener thread did that until the post-Phase 5/6 hardening). CI pip-installs it so its tests run. Understanding the three collaborators below explains most of the codebase.

- **`mu/app.py`** — entry point (`run()`). Builds the `QApplication`, splash screen, the `Window`, and the `Editor`, registers the list of mode classes, and wires logging. The core's modes are the import list at the top of this file + `mu/modes/__init__.py`; everything else comes from plugins (`setup_modes` → `load_plugins`).

- **`mu/logic.py`** — the **`Editor`** controller (non-GUI). Holds `self.modes` (a `dict` of name → mode instance), the current mode, and all the application logic: open/save/run, mode switching (`select_mode` / `change_mode`), flake8/pycodestyle checking, device detection (`Device` / `DeviceList`). The `Editor` talks to the UI only through the `view` object passed in — keep GUI code out of here; that separation is what makes `logic.py` unit-testable.

- **`mu/interface/`** — the Qt view layer. `interface/main.py` defines the **`Window`** class (the `view` the `Editor` drives). `editor.py` is the Scintilla-based text widget, `panes.py` the REPL/process-output/plotter panes, `dialogs.py` dialogs, `themes.py` the day/night/contrast stylesheets, `widgets.py` small shared widgets.

- **`mu/modes/`** — every mode subclasses **`BaseMode`** in `modes/base.py` (MicroPython-family modes subclass `MicroPythonMode`, which adds REPL/serial plumbing). A mode declares `name`, `description`, `icon`, and implements `actions()` (toolbar buttons), `api()` (autocomplete/calltip data), `workspace_dir()`, etc.; `uses_user_environment` (admin dialog env/packages tabs) and `ensure_workspace_assets(wd)` (called for every mode at startup) replace what used to be hardcoded per mode name — the core must not name plugin modes. New modes should be plugins (`docs/plugins.md`, template `plugins/example/`); a core mode is registered in `app.py` and `modes/__init__.py`. `modes/api/` holds generated API stubs (excluded from ruff, as are `plugins/*/nu_*/api`).

- **`mu/virtual_environment.py`** — Mu manages a **separate "user" virtualenv** (the `venv` singleton at module bottom) into which it installs third-party packages requested from the UI, isolated from Mu's own environment. Since Phase 4a it is driven by **uv**: `find_uv()` locates the binary (`MU_UV` → `uv` on `PATH` → the bundled `uv` wheel), `create_venv` builds it from the CPython bundled in installers (`mu/wheels/python/`, extracted once by `ensure_bundled_python` into `DATA_DIR/python/`; builds an upgrade left behind are deleted at startup by `remove_old_bundled_pythons` unless the env's `pyvenv.cfg` points into them) with `--seed --no-index`, so first launch is offline (dev checkouts without the bundle fall back to `uv venv --python <X.Y> --seed`), `Uv` wraps `uv pip`/`uv run` via `QProcess`, and `activation_vars()` activates the env for spawned user code (Run and the Jupyter kernel). Since Phase 4b (part 1) the env is **visible**: every uv command goes through `Uv` (`run_blocking`/`run`/`run_subprocess`/`script_command`), which records it in the GUI-free `mu/command_log.py` ("What Nu ran" on the admin dialog's Environment tab, and INFO in the log) — don't call uv around it; the status bar shows `Environment: <name> · Python X.Y` in modes with `uses_user_environment`; and `mu/script_metadata.py` (PEP 723) makes the Python 3 Run use `uv run --python <env python> --script <file>` for files with a `# /// script` block (see `docs/environment.md`). Bundled wheels live in `mu/wheels/` (`python -m mu.wheels --package` fetches them for installers): `wheels.baseline_packages()` = the core's `mode_packages` (ipykernel) + each installed plugin's `learner-env` extra, read from package metadata (`plugin_packages()`), never by importing the plugin.

- **`mu/plugin/`** — the public, versioned **plugin API** (Phase 5a; currently **0.5**, see `docs/plugins.md`): `PLUGIN_API_VERSION`, `Plugin` (`name`, `description`)/`ModePlugin` (+ `images`), `Mode` (= `BaseMode`), `MicroPythonMode`, `Device` (= `mu.logic.Device`), and the `Host` façade plugins use instead of `Editor`/`Window` (incl. `register_images`, `save_current`, `run_program`/`stop_program`, `update_action`, `python_apis`, `shared_apis`, `plotter_available`, and since 0.5 `log_command`, `current_device`, `data_dir`). Plugin images are searched after the core's by `mu.resources` (`register_image_dir`; a name clash raises, so the plugin is skipped). `app.setup_modes` registers the built-in modes through a `Host`, then `mu/plugin/loader.py` loads every enabled plugin found via entry points (group `mu.plugins`) or the drop-in folder `DATA_DIR/plugins/`, skipping (and logging) any that fail, with a `PluginRecord` each (`kind` bundled/package/folder — `loader.BUNDLED_DISTRIBUTIONS` must match the bundled `nu-*` deps — `problem`, `detail`) on `host.plugin_records`; `settings["disabled_plugins"]` switches plugins off (user settings are autosaved, and `set_plugin_enabled` saves at once). The admin dialog's **Plugins** tab (`dialogs.PluginsWidget`) shows `Host.describe_plugins()` and switches plugins from the next start via `Host.set_plugin_enabled` (the `Editor` reaches the Host as `editor.plugin_host`; no live unloading). Plugin errors never crash Nu: `mu/plugin/errors.py` guards a plugin mode's core-called methods, and `app.excepthook` / `app.thread_excepthook` (threads) hand plugin tracebacks to it first (dialog + log, rate limited, reported on the GUI thread, offer to switch off, marked in `plugins_switched_off_after_errors`); plugins raise `mu.plugin.PluginError` for expected, learner-fixable problems. Tests redirect the drop-in folder to a temp dir and reset the active error handler (autouse fixtures in the root `conftest.py`). `plugins/example/` is the template plugin; `plugins/pygamezero/` and `plugins/circuitpython/` (a `MicroPythonMode` with its own `adafruit-board-toolkit` dependency) the reference bundled plugins. Keep `mu.plugin`'s surface deliberate: anything exported there is a promise to plugin authors.

- **`mu/debugger/`** — the Python3 visual debugger, split into a `client` (in-process, talks to the UI) and a `runner` (the debugged program's subprocess). See `docs/debugger.md`.

Supporting modules: `mu/settings.py` + `mu/config.py` (persisted settings and path constants), `mu/i18n.py` + `mu/locale/` (gettext translations; `make translate_*` workflows), `mu/resources/` (icons, fonts, CSS, web assets).

## Where to read more

`docs/` is **MkDocs** source (Markdown, Material theme; `mkdocs.yml` at the repo root, published to GitHub Pages via `.github/workflows/docs.yml`). Build with `make docs` or live-preview with `make docs-serve`. Most useful for orientation: `docs/architecture.md`, `docs/modes.md` (writing a mode), `docs/debugger.md`, `docs/setup.md`, `docs/tests.md`, `docs/translations.md`, `docs/packaging.md`. Every class/method carries a human-written docstring; these are extracted into `docs/api.md` via mkdocstrings. Every page now describes Nu as it is (audited against the code for the docs-modernisation PR); `docs/design/*` keep Mu's original decision records as history, each followed by a **Nu today** section, and `user-experience.md` keeps Nicholas Tollervey's essay with a section on where Nu departs. The site is also Nu's only learner-facing documentation (`help.md` is what **Help** opens; `HELP_URL`/`PLUGINS_HELP_URL` in `mu/logic.py` link to `help/` and `plugins/`, so don't rename those pages); `docs/docs-site.md` covers how it's built and published. Check docs changes with `uv run --no-sync mkdocs build --strict`.
